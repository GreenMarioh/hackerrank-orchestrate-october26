## §1.2 Log Dialects Breakdown & Reconciliation

Line counts across all 26 `.log` evidence files:

| Dialect | Line Count | Number of Files | Representative Files |
|---------|-----------:|----------------:|----------------------|
| `key_value` | 1,546 | 22 | `service_events_ap_south_20260915.log`, `operations_stream_eu_central_20260705.log` |

| `syslog_rfc5424` | 232 | 2 | `syslog_archive_ap_southeast_20260325.log`, `syslog_archive_us_east_20260824.log` |
| **Total Lines** | **2,211** | **26** | **Unmatched lines: 0** |

### Reconciliation Note:
An initial profiling pass reported "2 active dialects" because the syslog archiver lines begin with an ISO ingestion timestamp prepended by the collection infrastructure (e.g. `2026-03-25T08:51:13Z <15>1 node-8 log_router ...`). A naive regex matching only `^<\d+>` treated those lines as plain key-value. Updating the tokenizer regex to recognize optional timestamp prefixes before the `<PRI>1` header (`^(?:\S+T\S+\s+)?<\d+>\d+\s+`) successfully separates all three distinct formats with 0 unmatched lines. All three tokenizers have unit tests in `code/tests/test_log_dialects.py`.

## §1.3 Hypothesis Results (H1 – H7)

### H1 — Linking window (events within ±N min of reported_at)
**Status: PARTIAL**
- **Evidence**: 76.6% (85/111) of sample resources appear within ±120 min (24.3% within 30m, 52.3% within 60m).
- **Counter-examples**: 26 of 111 expected resources (23.4%) have **no activity event at all** in `system_activity.csv`. They exist only within database replicas, exports, or log files.
- **Decision**: The time window is strictly a secondary candidate-generation heuristic and must be validated with a second signal. Primary linking must use evidence content matching.

### H2 — Anonymized Record Linking & Step Operation Recount
**Status: PARTIAL**
A precise breakdown of `sample_output.csv` reveals:
- **`ANONYMIZE_RECORD` (Remediation)**: Exactly 5 steps, all in `INCOMPLETE` cases (0 in COMPLETE, 0 in NOT_APPLICABLE). All 5 have `evidence_id = ""` because remediation describes future action.
- **`VERIFY_RECORD_ANONYMIZED` (Verification)**: Exactly 12 steps:
  - 7 steps in `COMPLETE` cases: each cites a concrete evidence file (e.g. `evidence_03`, `evidence_05`) proving the record was already anonymized at `audit_at`.
  - 5 steps in `INCOMPLETE` cases: each has `evidence_id = ""` representing post-remediation verification checks.
- **Findings**: 41 total findings across the 32 samples; **0 have empty evidence IDs**. Findings **always** cite participant-visible evidence.
- **Decision**: Anonymized records are linked through evidence content (when historical identifiers exist), catalog events, or resource-ID bridging across snapshots.

### H3 — LINK_RESOURCE_IDENTITY event authority
**Status: PARTIAL (Likely CONFIRMED for full dataset)**
- **Evidence**: Exactly 12 `LINK_RESOURCE_IDENTITY` events exist in `system_activity.csv` covering 12 distinct resource types (`account_5762`, `search_428`, `data_flow_1121`, `object_19`, `marketing_001`, `export_1260`, etc.).
- **Limitation**: None of these 12 resources belong to the 32 sample cases; they cover hidden test cases in the 518 evaluation set.
- **Decision**: Treat `LINK_RESOURCE_IDENTITY` as authoritative ownership evidence. Added synthetic unit tests in `code/tests/test_link_identity.py` to verify both inclusion and strict enforcement of the `audit_at` cutoff (`event_time <= audit_at`).

### H4 — Retention evidence (RETAIN_RECORD events + PDFs)

- **Decision**: `RETAIN_RECORD` events + PDF retention registers provide the grounded evidence for `VERIFY_RECORD_PRESENT`.

- Therefore, resources with prefix `object_` map to logical system `object_storage`.
